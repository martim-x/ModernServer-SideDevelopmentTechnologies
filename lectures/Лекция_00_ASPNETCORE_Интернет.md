# Лекция 00. Интернет (основы, HTTP, файлы проекта ASPA)

## Назначение
Базовые сведения, необходимые для понимания и защиты лабораторных: интернет и стек TCP/IP,
клиент-серверная архитектура, протокол HTTP (структура request/response, методы, коды состояния,
HTTPS), URL/URN, идемпотентность, сессии/куки. В конце — справочный блок по файлам проекта
ASP.NET Core и **готовые ответы на вопросы 17-29 из Лабораторной 1**.

## 1. Интернет и компоненты
- Интернет — всемирная компьютерная сеть, построенная на основе **стека протоколов TCP/IP**.
- Компоненты интернета: организации (**ISOC**), службы (**DNS**), стек протоколов **TCP/IP**,
  документации (**RFC**).

## 2. Клиент-серверная архитектура
Программа, состоящая из двух компонентов — клиента и сервера. Клиент и сервер взаимодействуют
в соответствии с заданными правилами (протоколами). **Инициатором соединения всегда является клиент.**

| Тип | Определение | Пример из лекции |
|---|---|---|
| **Симплекс** | передача только в одну сторону, без ответа | радио; сервер отправляет клиенту уведомления, но клиент не может ничего отправить в ответ |
| **Полудуплекс** | данные передаются в обе стороны, но поочерёдно | рация |
| **Дуплекс** | передача данных в обе стороны одновременно без ожидания | телефонный звонок |
| **Pub/Sub** | один «публикует» данные, другие «подписчики» получают их; публикующий не знает, кто подписался | — |

**Web-приложение** — клиент-серверное приложение, применяемое для обмена данными по протоколу HTTP;
может быть просто web-приложением (HTML+HTTP) или web-службой (**API**: HTTP-транспорт, форматы XML, JSON).

### Свойства и версии HTTP
| Версия | Свойство | Формат |
|---|---|---|
| HTTP/1 | полудуплекс | — |
| HTTP/1.1 | полудуплекс | текстовый |
| HTTP/2 | дуплекс | бинарный |
| HTTP/3 | черновой, не распространён | — |

## 3. Протокол HTTP
- Два типа абонентов: **клиент** и **сервер**.
- Два типа сообщений: **request** и **response**; от клиента к серверу — request, обратно — response.
- На один request всегда один response, иначе ошибка; одному response всегда один request.
- TCP-порты: **80** (HTTP), **443** (HTTPS).
- Для адресации используется **URI** или **URN**. Поддерживается W3C, описан в нескольких RFC.
- **Stateless-протокол** — когда сервер не хранит информацию о предыдущих запросах, каждый запрос
  изолирован от другого.

### Структура запроса (Request)
- метод;
- URI;
- версия протокола (HTTP/1.1);
- заголовки (пары: имя/значение);
- параметры (пары: имя/значение);
- расширение.

### Структура Response
- версия протокола (HTTP/1.1);
- код состояния (1xx, 2xx, 3xx, 4xx, 5xx);
- пояснение к коду состояния;
- заголовки (пары: имя/значение);
- расширение.

### Группы заголовков
| Группа | Назначение |
|---|---|
| **General** | общие заголовки, используются в запросах и ответах |
| **Request** | используются только в запросах |
| **Response** | используются только в ответах |
| **Entity** | для сущности в ответах и запросах |

### Методы запроса
| Метод | Назначение |
|---|---|
| OPTIONS | Запрашивает информацию о поддерживаемых методах для ресурса |
| GET | Запрашивает данные с сервера |
| HEAD | Запрашивает заголовки ответа без тела |
| POST | Отправляет данные на сервер для обработки |
| PUT | Обновляет существующий ресурс или создает новый |
| DELETE | Удаляет указанный ресурс с сервера |
| TRACE | Возвращает данные, отправленные клиентом, для диагностики |
| CONNECT | Устанавливает туннель к серверу (обычно для прокси) |
| PATCH | Частично обновляет ресурс |

### Коды состояния
| Диапазон | Значение |
|---|---|
| 1xx | информационные сообщения |
| 2xx | успешный ответ |
| 3xx | переадресация |
| 4xx | ошибка клиента |
| 5xx | ошибка сервера |

### HTTPS — процедура рукопожатия
HTTPS — защищенная версия HTTP, использующая шифрование для конфиденциальности и целостности
данных при передаче между клиентом (например, браузером) и сервером.
**Рукопожатие** — процесс согласования параметров и установления соединения между двумя сторонами.
1. Инициация: клиент запрашивает защищенное соединение (HTTPS).
2. Сертификат: сервер отправляет свой SSL/TLS сертификат с публичным ключом.
3. Проверка: клиент проверяет подлинность сертификата через CA.
4. Генерация ключа: клиент создает предварительный сеансовый ключ и шифрует его публичным ключом сервера.
5. Отправка ключа: клиент отправляет зашифрованный ключ на сервер.
6. Дешифровка: сервер дешифрует ключ с помощью своего приватного ключа.
7. Установка ключа: оба устройства имеют общий сеансовый ключ.
8. Завершение: клиент и сервер подтверждают завершение рукопожатия и начинают обмен зашифрованными данными.

## 4. URL, URN, идемпотентность
- **URL: Uniform Resource Location** — унифицированный локатор ресурса, содержащий местонахождение
  ресурса и способ обращения (протокол) к ресурсу; описывает множество URI.
- **URN: Uniform Resource Name** — унифицированное имя ресурса, URI без месторасположения и способа
  доступа. В будущем URN должен заменить URL (для решения проблем с перемещением ресурсов в Internet).
- **Идемпотентность** — свойство операции, означающее, что повторное выполнение даст тот же результат,
  что и первое: «если ты выполнишь операцию один раз или несколько раз подряд, результат будет
  одинаковым». Идемпотентны **GET, PUT, DELETE**.

## 5. Сессия, куки, хранение состояния
- **Сессия** — серверный объект, хранящий информацию о соединении с клиентом, создаётся при первом
  обращении. Время жизни: **timeout** (системный параметр, обычно 10–30 минут) — максимальное время
  между запросами клиента. **Живёт на стороне сервера.**
- **Куки (Cookie)** — фрагмент данных, отправленный web-сервером и хранимый web-клиентом.
  Используется для аутентификации, хранения пользовательских предпочтений, статистики, информации
  о сеансе (обычно Session ID). Обычно имеет имя, содержащее URL, может иметь срок действия.
  Для создания и пересылки применяются заголовки. **Живёт на стороне клиента.**

### Способы передачи параметров от клиента на сервер
- URI;
- заголовки;
- расширение (тело).

### Способы сохранить состояние в HTTP
1. Cookie
2. Session
3. sessionstorage
4. Url storage
5. localstorage

## 7. Разница между режимами Release и Debug
В ТЗ лабы 1 (п.7) требуется объяснить разницу, но **ответа в тексте лекции 00 нет** — только
упоминание задания. Опора (общее знание ASP.NET Core): Debug — режим отладки, без оптимизации,
с дополнительной диагностикой, условные блоки `#if DEBUG` компилируются; Release — оптимизированная
компиляция, без отладочной информации, выход в отдельный каталог (`bin/Release/<TFM>/`).
(В ТЗ это вопрос к защите, а не факт из лекции.)
