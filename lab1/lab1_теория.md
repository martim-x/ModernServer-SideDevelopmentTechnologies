## 1. Интернет и клиент-серверная архитектура

**Интернет** — всемирная компьютерная сеть, построенная на основе стека протоколов TCP/IP.

Компоненты интернета:

| Компонент | Пример |
|---|---|
| Организации | ISOC (Internet Society) |
| Службы | DNS |
| Стек протоколов | TCP/IP |
| Документация | RFC |

**Клиент-серверная архитектура** — программа, состоящая из двух компонент — клиента и сервера. Клиент и сервер взаимодействуют между собой в соответствии с заданными правилами (протоколами). **Инициатором соединения всегда является клиент.**

### Типы передачи данных

- **Дуплекс** — передача данных в обе стороны одновременно без ожидания (телефонный звонок).
- **Полудуплекс** — данные передаются в обе стороны, но в любой момент времени передаёт только одна сторона, поочерёдно (рация).
- **Симплекс** — передача только в одну сторону без ответа: один отправляет, один получает (радио; сервер шлёт клиенту уведомления, но клиент не может ответить).
- **Pub/Sub** — модель взаимодействия, где один «публикует» данные, а «подписчики» получают их. Публикующий не знает, кто подписался, а подписчики просто получают данные, как только те появляются.

### Web-приложение

Клиент-серверное приложение, применяющее для обмена данными протокол HTTP. Может быть:

- **просто web-приложением** (HTML + HTTP);
- **web-службой** (API, HTTP-транспорт, форматы XML, JSON).

## 2. Протокол HTTP

**HTTP** (HyperText Transfer Protocol) — протокол прикладного уровня для передачи данных в web.

### Свойства HTTP

- Два типа абонентов: **клиент** и **сервер**.
- Два типа сообщений: **request** (запрос) и **response** (ответ).
- От клиента к серверу — request; от сервера к клиенту — response.
- **На один request — ровно один response**, иначе ошибка.
- Одному response — ровно один request, иначе ошибка.
- **Stateless** — сервер не хранит информацию о предыдущих запросах, каждый запрос изолирован от другого.
- TCP-порты: **80** (HTTP), **443** (HTTPS).
- Для адресации используется URI или URN.
- Протокол разрабатывает и поддерживает **IETF** (Internet Engineering Task Force), рабочая группа HTTPBIS; современная спецификация — серия RFC: **9110** (семантика), **9112** (HTTP/1.1), **9113** (HTTP/2), **9114** (HTTP/3). W3C участвовал в разработке исторически (1990-е), сейчас ведёт веб-API поверх HTTP (Fetch, CORS и т.п.).

### Версии HTTP

| Версия | Режим | Особенности |
|---|---|---|
| HTTP/1.0 | полудуплекс | устаревшая, одно соединение — один запрос |
| HTTP/1.1 | полудуплекс | действующий, текстовый; keep-alive, pipelining |
| HTTP/2 | дуплекс | бинарный; мультиплексирование потоков в одном TCP-соединении, сжатие заголовков HPACK, server push |
| HTTP/3 | дуплекс | RFC 9114 (Proposed Standard, июнь 2022); работает поверх **QUIC/UDP**, а не TCP; встроенный TLS 1.3, нет head-of-line blocking на уровне транспорта; поддерживается всеми основными браузерами и CDN |

### HTTPS и рукопожатие

**HTTPS** — защищённая версия HTTP, использующая шифрование (SSL/TLS) для обеспечения конфиденциальности и целостности данных при передаче между клиентом и сервером.

**Рукопожатие** — процесс согласования параметров и установления соединения между двумя сторонами:

1. **Инициация** — клиент запрашивает защищённое соединение (HTTPS).
2. **Сертификат** — сервер отправляет свой SSL/TLS-сертификат с публичным ключом.
3. **Проверка** — клиент проверяет подлинность сертификата через CA (центр сертификации).
4. **Генерация ключа** — клиент создаёт предварительный сеансовый ключ и шифрует его публичным ключом сервера.
5. **Отправка ключа** — клиент отправляет зашифрованный ключ на сервер.
6. **Дешифровка** — сервер дешифрует ключ своим приватным ключом.
7. **Установка ключа** — обе стороны имеют общий сеансовый ключ.
8. **Завершение** — стороны подтверждают завершение рукопожатия и начинают обмен зашифрованными данными.

### Структура запроса (Request)

```
метод URI версия-протокола (HTTP/1.1)
заголовки (пары: имя/значение)
параметры (пары: имя/значение)
расширение (тело)
```

### Группы заголовков

| Группа | Где используется |
|---|---|
| **General** | общие — и в запросах, и в ответах |
| **Request** | только в запросах |
| **Response** | только в ответах |
| **Entity** | для сущности (тела) в запросах и ответах |

### Методы запроса

| Метод | Назначение |
|---|---|
| **OPTIONS** | запрашивает информацию о поддерживаемых методах для ресурса |
| **GET** | запрашивает данные с сервера |
| **HEAD** | запрашивает заголовки ответа без тела |
| **POST** | отправляет данные на сервер для обработки |
| **PUT** | обновляет существующий ресурс или создаёт новый |
| **DELETE** | удаляет указанный ресурс с сервера |
| **TRACE** | возвращает данные, отправленные клиентом, для диагностики |
| **CONNECT** | устанавливает туннель к серверу (обычно для прокси) |
| **PATCH** | частично обновляет ресурс |

### Структура ответа (Response)

```
версия-протокола (HTTP/1.1)
код состояния (1xx–5xx)
пояснение к коду состояния
заголовки (пары: имя/значение)
расширение (тело)
```

### Коды состояния

- **1xx** — информационные сообщения;
- **2xx** — успешный ответ;
- **3xx** — переадресация;
- **4xx** — ошибка клиента;
- **5xx** — ошибка сервера.

### Идемпотентность

Свойство операции: повторное выполнение даёт тот же результат, что и первое. Выполни операцию один раз или несколько подряд — результат одинаков. Идемпотентные методы: **GET, PUT, DELETE**.

### URI, URL, URN

- **URI** — унифицированный идентификатор ресурса (общее понятие).
- **URL** (Uniform Resource Location) — унифицированный **локатор** ресурса: содержит местонахождение ресурса и способ обращения (протокол) к нему. Описывает множество URI.
- **URN** (Uniform Resource Name) — унифицированное **имя** ресурса: URI, не содержащее месторасположение и способ доступа. В будущем URN должен заменить URL (чтобы решить проблемы с перемещением ресурсов в Internet).

## 3. Состояние в HTTP: сессии, куки, хранилища

HTTP stateless, но состояние сохранить можно:

### Сессия

Серверный объект, хранящий информацию о соединении с клиентом; создаётся при первом обращении. **Живёт на стороне сервера.**

**Время жизни** — timeout (системный параметр, обычно 10–30 минут): максимальное время между запросами клиента.

### Cookie

Фрагмент данных, отправленный web-сервером и хранимый web-клиентом. **Живёт на стороне клиента.** Используется для:

- аутентификации;
- хранения пользовательских предпочтений;
- статистики;
- информации о сеансе (обычно Session ID).

Обычно имеет имя, содержащее URL, и может иметь срок действия. Создание и пересылка выполняются через заголовки.

### Способы передачи параметров от клиента на сервер

- URI;
- заголовки;
- расширение (тело запроса).

### Все способы сохранить состояние

- Cookie;
- Session;
- sessionStorage;
- URL storage (параметры в адресе);
- localStorage.

## 4. Платформа .NET и ASP.NET Core

### Что такое фреймворк?

Каркас приложения: набор библиотек плюс заданная архитектура и точки расширения. Ключевое отличие от библиотеки — **инверсия управления**: библиотеку вызываете вы, а фреймворк вызывает ваш код в нужный момент. Фреймворк диктует структуру программы, а вы дописываете недостающие части: обработчики, контроллеры, конфигурацию.

### Что такое фреймворк операционной системы?

Набор системных библиотек и API, поставляемых вместе с ОС и жёстко к ней привязанных: Win32/WinAPI и .NET Framework в Windows; Cocoa, Foundation, AppKit в macOS (там это буквально каталоги `*.framework`). Даёт доступ к службам конкретной ОС — окнам, файловой системе, сети, реестру. Противоположность — кроссплатформенный фреймворк вроде ASP.NET Core.

### Что такое программная платформа?

Совокупность среды исполнения, библиотек, компиляторов и инструментов, на которой создаются и работают программы. Платформа отвечает на вопрос «**на чём** это выполняется», фреймворк — «**по каким правилам** это написано». .NET — платформа; ASP.NET Core — фреймворк на этой платформе.

### Что такое .NET?

Кроссплатформенная платформа разработки Microsoft с открытым исходным кодом (MIT). Состав:

- **CoreCLR** — среда исполнения: JIT-компилятор, сборщик мусора, загрузчик сборок;
- **BCL** — библиотека базовых классов (пространства `System.*`);
- **компиляторы** — Roslyn (C#), компиляторы VB и F#;
- **SDK** — утилита `dotnet`, MSBuild, шаблоны проектов, клиент NuGet.

Компиляция двухступенчатая: исходный код → промежуточный язык IL (сборка `.dll`) → машинный код при первом вызове метода (JIT) либо при публикации (AOT). С .NET 5 — единая платформа, заменившая .NET Framework, .NET Core и Mono; мажорные версии выходят каждый ноябрь.

### Что такое ASP.NET Core?

Веб-фреймворк платформы .NET для серверных приложений: сайты, REST API, real-time (SignalR), Blazor. Построен на двух идеях:

- **внедрение зависимостей (DI)**;
- **конвейер middleware**, через который последовательно проходит каждый запрос.

Включает собственный веб-сервер **Kestrel**, подсистемы конфигурации, логирования, маршрутизации, аутентификации и авторизации. Модели программирования: minimal API, MVC, Razor Pages.

### Кроссплатформенность ASP.NET Core

Один и тот же исходный код и одни и те же IL-сборки работают на Windows, Linux, macOS (x64, ARM64): под каждую ОС есть своя реализация рантайма, а Kestrel не зависит от IIS. Следствие: разработка на macOS, продакшн на Linux в Docker. Ограничение: платформозависимые вещи (реестр Windows, интеграция с IIS, часть `System.Drawing`) недоступны.

### Что такое NuGet?

Менеджер пакетов .NET. Пакет — файл `.nupkg` (zip со сборками, метаданными и списком зависимостей). Публичный репозиторий — nuget.org, клиент встроен в `dotnet`. Зависимость объявляется в `.csproj` элементом `PackageReference`, восстанавливается `dotnet restore` в кеш `~/.nuget/packages`, граф версий — в `obj/project.assets.json`.

### Утилита dotnet

Единый интерфейс командной строки к SDK и одновременно хост рантайма:

| Команда | Назначение |
|---|---|
| `dotnet new` | создание проектов и решений из шаблонов |
| `dotnet restore` | восстановление NuGet-зависимостей |
| `dotnet build` | компиляция в IL |
| `dotnet run` | сборка и запуск проекта |
| `dotnet App.dll` | запуск уже собранного приложения (режим хоста) |
| `dotnet test` | запуск тестов |
| `dotnet publish` | подготовка к развёртыванию |
| `dotnet add/list/remove package` | управление зависимостями |
| `dotnet sln` | управление составом решения |
| `dotnet --info` | диагностика окружения |

### CoreCLR и CoreFX

- **CoreCLR** — среда исполнения (виртуальная машина) .NET, кроссплатформенная реализация CLR: загрузка сборок, JIT-компиляция (RyuJit) IL в машинный код, сборка мусора, исключения, потоки, P/Invoke. Альтернатива — Native AOT.
- **CoreFX** — историческое название библиотеки классов .NET Core (коллекции, IO, LINQ, сеть). Репозиторий `dotnet/corefx` в 2019 объединён с `coreclr` в `dotnet/runtime`. Пара «CoreCLR + CoreFX» = «рантайм + библиотека классов».

### Встроенный HTTP-сервер ASP.NET Core

**Kestrel** — кроссплатформенный асинхронный веб-сервер внутри процесса приложения (виден в заголовке ответа `Server: Kestrel`). Работает как пограничный сервер или за реверс-прокси (Nginx, IIS, Apache). Альтернативы: HTTP.sys (только Windows), IIS Express (отладка).

### Последняя устойчивая версия

**.NET 10 / ASP.NET Core 10.0** — LTS, ноябрь 2025. Мажорные версии — ежегодно в ноябре: чётные LTS (длинная поддержка), нечётные STS (короткая). .NET 8 — тоже LTS, поддержка до 10 ноября 2026; .NET 7 снят с поддержки в мае 2024.

## 5. Состав проекта ASP.NET Core (задания 4, 8–10)

### ASPA001.csproj

> В задании он назван `.cproj` — это опечатка; правильное расширение — `.csproj`.

Файл проекта C# в формате MSBuild (XML): содержит список файлов, включённых в проект, ссылки на системные сборки, целевую платформу и параметры компиляции. Полностью описывает, **что и как собирать**.

```xml
<Project Sdk="Microsoft.NET.Sdk.Web">
  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>
</Project>
```

- `Sdk="Microsoft.NET.Sdk.Web"` — правила сборки веб-приложений: ссылка на shared framework ASP.NET Core, авто-включение всех `.cs`, копирование `appsettings*.json`, поддержка `wwwroot`;
- `TargetFramework` — целевая платформа (доступный API и рантайм);
- `Nullable` — анализ ссылочных типов на `null` при компиляции;
- `ImplicitUsings` — неявные глобальные `using`;
- сюда же добавляются `PackageReference` и `ProjectReference`.

### Program.cs

Точка входа приложения. Порядок: создание построителя хоста → регистрация сервисов в DI-контейнере → построение конвейера middleware и маршрутов → запуск сервера.

Шаблон (top-level statements) и явная запись в стиле `Program.Main` (задание 11):

```csharp
internal class Program
{
    private static void Main(string[] args)
    {
        // Построитель: конфигурация, логирование, DI, Kestrel.
        var builder = WebApplication.CreateBuilder(args);

        // Регистрация сервисов — строго ДО Build().
        // builder.Services.AddHttpLogging(...);

        // Фиксация конфигурации и контейнера.
        var app = builder.Build();

        // Конвейер middleware: порядок Use* задаёт порядок обработки запроса.
        // app.UseHttpLogging();

        // Маршрут: GET "/" возвращает строку в теле ответа.
        app.MapGet("/", () => "Hello World!");

        // Kestrel открывает TCP-порт и блокирует поток до остановки.
        app.Run();
    }
}
```

Top-level statements — синтаксический сахар: компилятор сам оборачивает файл в класс `Program` с методом `Main`; `args` — параметр этого метода.

### appsettings.json

Конфигурация приложения, читается при запуске: уровни логирования, строки подключения, собственные секции. Меняется без перекомпиляции, копируется в `bin` и разворачивается вместе с приложением.

Порядок источников конфигурации (каждый следующий перекрывает предыдущий):

1. `appsettings.json`;
2. `appsettings.{Environment}.json`;
3. User Secrets (только Development);
4. переменные окружения;
5. аргументы командной строки.

`AllowedHosts` — фильтр допустимых значений заголовка `Host` (защита от host header injection), `*` — «разрешены любые».

### Properties/launchSettings.json

Настройки **только локального запуска** из IDE и `dotnet run`; в опубликованное приложение не попадают. Профили запуска: переменные окружения, открытие браузера, адреса прослушивания.

**TCP-порт задаётся здесь** — в `profiles → <профиль> → applicationUrl` (для IIS Express — отдельно, в секции `iisSettings`):

```json
"profiles": {
  "http":  { "applicationUrl": "http://localhost:5255" },
  "https": { "applicationUrl": "https://localhost:7141;http://localhost:5255" }
}
```

Переопределить порт без правки файла: `dotnet run --urls http://localhost:5080` или `ASPNETCORE_URLS=http://localhost:5080`.

### bin/ и obj/

- `obj/` — промежуточные результаты: граф зависимостей `project.assets.json`, сгенерированный код;
- `bin/<Конфигурация>/net8.0/` — готовая сборка.

Оба каталога генерируются автоматически, в git не коммитятся.

## 6. Debug и Release (задание 6)

| | Debug | Release |
|---|---|---|
| Оптимизация IL (`Optimize`) | выключена | включена |
| Константы компиляции | `DEBUG`, `TRACE` | только `TRACE` |
| Инлайнинг методов, свёртка кода | нет | да |
| `Debug.Assert`, `Debug.WriteLine` | работают | вырезаются компилятором |
| Скорость выполнения | ниже | выше |
| Отладка по шагам | точное соответствие строкам | строки «съезжают» из-за оптимизаций |
| Каталог вывода | `bin/Debug/` | `bin/Release/` |
| Назначение | разработка и отладка | поставка, продакшн |

`.pdb` (отладочные символы) создаётся в обеих конфигурациях; разница — в оптимизации и константах компиляции. Из-за оптимизаций отладчик в Release работает непредсказуемо: переменные «оптимизированы», точки останова смещаются, стектрейсы короче.

## 7. Запуск без Visual Studio (задание 7)

Минимальный набор файлов для переноса (framework-dependent):

| Файл | Зачем |
|---|---|
| `ASPA001.dll` | код в IL — главный файл |
| `ASPA001.runtimeconfig.json` | какой рантайм грузить; без него хост не стартует |
| `ASPA001.deps.json` | список зависимостей для загрузчика сборок |
| `appsettings.json` | конфигурация |
| `ASPA001` / `.exe` | запуск без `dotnet` (apphost) |

Запуск:

```bash
dotnet ASPA001.dll   # через утилиту dotnet — кроссплатформенно
./ASPA001            # через apphost; на Windows — ASPA001.exe
```

На macOS/Linux файла `.exe` нет — apphost называется `ASPA001`; `.exe` появляется при сборке на Windows или публикации `-r win-x64`. Правильный способ получить набор — `dotnet publish` (self-contained с `-r osx-arm64 --self-contained` работает даже без установленного .NET, ~70 МБ).

## 8. Стадии подготовки и запуска ASPA

1. **restore** — разбор `.csproj`, разрешение NuGet-зависимостей, `obj/project.assets.json`;
2. **build** — Roslyn компилирует C# в IL; в `bin/` появляются `.dll`, `.deps.json`, `.runtimeconfig.json`, apphost, `appsettings*.json`;
3. **publish** — самодостаточный набор для развёртывания;
4. **старт процесса** — apphost или `dotnet` читает `runtimeconfig.json`, находит рантайм, инициализирует CoreCLR, вызывает `Main`;
5. **построение хоста** — `WebApplication.CreateBuilder(args)`: конфигурация, логирование, DI, Kestrel;
6. **регистрация сервисов** в DI-контейнере;
7. **`builder.Build()`** — контейнер «запечатывается», создаётся `WebApplication`;
8. **построение конвейера** middleware и маршрутов;
9. **`app.Run()`** — Kestrel открывает TCP-порт и слушает соединения;
10. **обработка запроса** — сокет → Kestrel → конвейер middleware → endpoint → ответ;
11. **остановка** — по сигналу (Ctrl+C, SIGTERM) активные запросы доигрываются, ресурсы освобождаются.
